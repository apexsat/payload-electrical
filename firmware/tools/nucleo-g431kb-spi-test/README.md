# NUCLEO-G431KB SPI bench test for PIB Test 2 (SPI portion only)

PIB Test 2 requires: *"demonstrate SPI & I2C interfaces by sending telemetry to Raspberry Pi."*

This project covers **only the SPI part**, and it uses a NUCLEO-G431KB in place of the Raspberry Pi. The Nucleo acts as the SPI controller. It reads the PIB's status and uptime telemetry about every 500 ms and checks that the data is real and that it changes over time. **I²C is not tested here.** A pass from this project means "SPI telemetry demonstration passed". It does **not** mean PIB Test 2 is complete.

The PIB firmware is not modified. The PIB runs its normal firmware from the `firmware/` project.

## 2. Nucleo configuration (as built)

| Setting | Value |
|---|---|
| SPI | SPI1, full-duplex master, 8-bit, MSB first |
| Mode | Mode 0: CPOL = low, CPHA = 1st edge |
| Chip select | Software (NSS disabled). PA11 is a push-pull GPIO that starts **high**. |
| System clock | HSI 16 MHz, no PLL. AHB ÷1, APB2 ÷1, so PCLK2 = 16 MHz. |
| SPI clock | SPI1 runs on APB2: 16 MHz ÷ 128 (prescaler) = **125.0 kHz** nominal. HSI16 tolerance is listed in the datasheet section "HSI16 oscillator characteristics". The firmware computes the rate at runtime from the real clock tree and stores it in `spi_test.sck_hz`. |
| Transfers | Blocking `HAL_SPI_TransmitReceive`, 10 ms timeout, no DMA, no RTOS |
| Debug | SWD on PA13/PA14 is kept. PB3 (SWO) and PB4/PB5 are not needed for SWD. Leave Serial Wire Viewer (SWV) **off**. |
| Extras | MISO (PB4) has an internal pull-down. A disconnected MISO line therefore reads as all-zero bytes, which the test rejects. The USB-PD dead-battery pull-down on PB4 is disabled at boot (`HAL_PWREx_DisableUCPDDeadBattery`). |

To change the SPI speed, open the `.ioc` in STM32CubeMX, go to SPI1 → Parameter Settings → Prescaler, and click Generate Code. For example, 256 gives 62.5 kHz.

## 3. Protocol (taken from the current PIB source)

The PIB is an SPI slave on SPI1, configured with hardware NSS, mode 0 and 8-bit frames (`firmware/Core/Src/main.c`, `MX_SPI1_Init`). It handles a frame **when CS rises**: `firmware/Board/Src/spi_slave.c` catches the rising edge on PA4 with EXTI4. It then passes the received bytes to `telemetry_on_spi_frame()` (`firmware/App/Src/telemetry.c`), loads the reply into its transmit buffer, and re-arms. The reply therefore goes out in the **next** CS-low transaction.

Each poll runs these steps:

1. CS low. Send `[0x80 | 0x00, 0x05]`, meaning "read 5 bytes starting at register 0x00". CS high. The bytes received during this transaction are discarded.
2. Wait 5 ms (`HAL_Delay(5)`, which actually waits 5–6 ms).
3. CS low. Send five `0x00` dummy bytes and receive the reply. CS high. The PIB ignores a frame whose first byte is `0x00`, so the dummy bytes cannot act as a command.
4. Wait for the next 500 ms poll.

Reply layout (`telemetry_update_snapshot`):

| Byte | Meaning |
|---|---|
| 0 | Status register 0x00. Bit 0 = ARMED is the only bit the current firmware sets. **Expected 0x00.** |
| 1–4 | Uptime register 0x01: little-endian IEEE-754 `float` in seconds (`HAL_GetTick()/1000`). The PIB refreshes it every 100 ms. |

CS goes high after every transfer, including failed ones. A failed transfer also calls `HAL_SPI_Abort`. The Nucleo only ever sends read requests and dummy bytes, never a write or actuator command.

## 4. Wiring

### 4.1 Signal table

PIB J3 connections were checked against `200_40 PIB/PIB.kicad_pcb`. Each J3 signal pin goes through a 22 Ω series resistor to the PIB MCU, and each has a PESD3V3 TVS diode to GND.

| Signal | Nucleo header label | Nucleo MCU pin | PIB J3 pin | PIB net → PIB MCU |
|---|---|---|---|---|
| SCK | **A4** | PA5 | **8** | EXT_SPI_SCK → R23 → PA5 |
| MISO (PIB → Nucleo) | **D12** | PB4 | **6** | EXT_SPI_MISO → R24 → PA6 |
| MOSI (Nucleo → PIB) | **D11** | PB5 | **7** | EXT_SPI_MOSI → R25 → PA7 |
| CS (active low) | **D10** | PA11 | **9** | EXT_SPI_~CS → R22 → PA4 |
| GND | **GND** | — | **14** | GND (pins 15–19, 25 and 26 are also GND) |

> **This differs from the originally proposed wiring.** On the NUCLEO-G431KB, header pin **D13 is connected to PB8, the green LED LD2**, not to PB3. This is set by solder bridges SB7 ON / SB6 OFF in the default build. PB3 only reaches D13 if those bridges are re-soldered. SCK therefore uses **PA5 on header pin A4**, which is SPI1_SCK. ST's own NUCLEO-G431KB SPI example uses the same pin. **Do not connect anything to D13.**
>
> Sources for the pin mapping:
> - ST's NUCLEO-G431KB example readmes in STM32Cube FW_G4 V1.6.3 give PA11 = pin 13 of the digital-side connector (D10) and PA5 = pin 8 of the analog-side connector (A4).
> - ST's stm32duino board file `variant_NUCLEO_G431KB.h` gives D10 = PA11, D11 = PB5, D12 = PB4, D13 = PB8 (LED, SB7 ON / SB6 OFF), and PB3 = "D13 if SB7 OFF SB6 ON".
> - CubeMX's board file for this Nucleo labels PB3 as `T_SWO`, which goes to the ST-LINK.
>
> I could not download ST user manual UM2397 to cross-check, because st.com timed out. Before wiring, open UM2397 (the NUCLEO-G431KB user manual) and confirm the Arduino Nano pinout table and the solder-bridge table (SB2, SB3, SB6, SB7) match the table above. If they don't match, stop.

Side effect to know about: by default **A4 (PA5) is also connected to D4 (PB7) through SB3**. Leave D4 unconnected. The firmware never configures PB7, so it stays a high-impedance input.

### 4.2 Do not connect

- PIB J3 pins **1–3 (VBAT_HOT)**, **4–5 (+3.3V)**, **12–13 (+5V)**, **20–21 (I²C)**, **22–24**.
- Nucleo **3V3, 5V, VIN, D13, D4**.
- No power wire between the boards. **GND is the only shared conductor.**

### 4.3 Connector orientation checks (do these with both boards unpowered)

J3 is a Harwin Gecko 2×13, 1.25 mm pitch connector (G125-MS12605M2P). Pins 1–13 form one row and pins 14–26 the other. Pin 14 sits directly across from pin 1. Gecko cable wire numbering and colour depend on the cable assembly, so **don't trust colours; check with a multimeter in continuity mode**. `200_40 PIB/bom/ibom.html` (open it in a browser) shows where J3 and R22–R25 are on the board.

1. **GND:** your GND wire (at J3 pin 14) should beep against a known PIB ground, such as J3's metal mounting tabs (MP pads).
2. **Signals:** each signal wire should beep (about 0 Ω) to the J3-side pad of its series resistor: SCK → R23, MISO → R24, MOSI → R25, CS → R22. The other pad of each resistor reads about 22 Ω.
3. **No shorts:** none of the four signal wires should beep to GND, to any other signal wire, or to J3 pins 1–5 or 12–13. The TVS diodes may give a diode-type reading to GND, but they must not beep.
4. At the Nucleo end, check the silkscreen labels **A4, D10, D11, D12, GND** next to each header pin.

Keep the wires short, under about 15 cm if possible.

## 5. Power arrangement

- **Nucleo:** USB cable from the Mac into the Nucleo's own USB connector (its on-board ST-LINK). Nothing else.
- **PIB:** currently powered from a separate ST-LINK's "3.3 V" pin. **This must be verified before use.** I have not confirmed:
  - **Which ST-LINK model it is.** On genuine ST probes (for example STLINK-V3), the 3.3 V-looking pin is often **VTref, a voltage-sense input that supplies no power**. Some ST-LINK/V2 clones have a real 3.3 V output.
  - **How much current that output can supply** compared with the PIB's 3.3 V draw.
  - **Where on the PIB that 3.3 V enters**, and whether it is the PIB's +3.3V rail.

  Check these against the probe's documentation and the PIB schematic. If the supply is weak, the PIB may reset repeatedly (brown-out), and `spi_test.uptime_resets` will count up.
- **Never connect the Nucleo's 3V3/5V to the PIB, or the PIB's J3 pins 4–5 (+3.3V) to anything.**
- **Power order:** power the **PIB first**, then plug in the Nucleo. When shutting down, unplug the **Nucleo first**. Reason: the Nucleo holds CS high (3.3 V). If the PIB is unpowered, that voltage would feed into the PIB MCU through only 22 Ω and its pin protection diodes.
- **Actuators:** keep all valve, heater, igniter and discharge loads **disconnected**. The Nucleo sends no commands. `host_test` confirms the PIB's command queue stays empty.

The project is already generated. You don't need to run CubeMX unless you change the `.ioc`.

2. **File → Import… → General → Existing Projects into Workspace → Next**.
3. **Select root directory → Browse…** and choose `payload-electrical/firmware/tools/nucleo-g431kb-spi-test`. Choose this folder itself, not `firmware/`.

5. **Finish**.

### 6.2 Build

1. Click the project name in the **Project Explorer**.
2. Click the **hammer** icon (Build, Debug configuration).
3. The **Console** should end with `Build Finished. 0 errors, 0 warnings.`

### 6.3 Regenerating from the .ioc (only if you change it)

STM32CubeIDE 2.x no longer includes CubeMX, so use the separate **STM32CubeMX** app:

1. **File → Load Project** and pick the `.ioc`.
2. Make your changes.
3. Click **GENERATE CODE**.

CubeMX keeps everything inside `USER CODE BEGIN/END` blocks, and it never touches `spi_telemetry_test.c/.h`.

### 6.4 Pick the right ST-LINK when both are plugged in

Each ST-LINK has a serial number. Point the debugger at the Nucleo's serial number, so you can't accidentally flash the Nucleo test onto the PIB, or the PIB firmware onto the Nucleo.

1. Find the Nucleo's serial number:
   1. Unplug the PIB's ST-LINK.
   2. In CubeIDE: **Run → Debug Configurations…**
   3. Double-click **STM32 C/C++ Application** to create `nucleo-g431kb-spi-test Debug`.
   4. On the **Debugger** tab, tick **ST-LINK S/N** and click **Scan**. Only the Nucleo appears. Write down its number.
   5. Plug the PIB's ST-LINK back in and click **Scan** again. The new number is the PIB's.

   From the terminal, `st-info --probe` (already installed via Homebrew) also lists the serial of each connected probe.
2. In `nucleo-g431kb-spi-test Debug` → **Debugger** tab:
   - **Debug probe:** ST-LINK (ST-LINK GDB server)
   - **Interface:** SWD
   - Tick **ST-LINK S/N** and select the **Nucleo's** number
   - **Serial Wire Viewer (SWV):** disabled
   - Click **Apply**.
3. In the PIB project's debug configuration (`firmware Debug`), likewise tick **ST-LINK S/N** and select the **PIB's** number.

You only run one debug session at a time here, so the default GDB port (61234) is fine. If you ever debug both boards at once, change one configuration's port, for example to 61244.

### 6.5 Run the PIB normally

1. Flash the PIB with its normal firmware from the `firmware` project at the commit you are testing. Use **Run** (green ▶ with the PIB's configuration), not Debug. Run flashes the board, resets it and lets it run with no debugger attached. If you used Debug instead, click **Terminate and disconnect** (red ■) afterwards, then press the PIB's reset button or power-cycle it.
2. Check the PIB is running: its **DEBUG_LED** toggles every 500 ms.
3. Leave the PIB's ST-LINK connected only if it supplies the PIB's power (see section 5).

### 6.6 Debug the Nucleo and watch the variables

1. Select `nucleo-g431kb-spi-test Debug` and click **Debug** (bug icon). CubeIDE flashes the Nucleo and stops at `main()`.
2. Press **Resume** (F8).
3. Open **Window → Show View → Live Expressions**. Click **Add new expression** and type `spi_test`. Expand it. Live Expressions refresh while the program runs. You can also press **Suspend** (pause) and look in the Expressions/Variables view.
4. The green **LD2** LED on the Nucleo shows the result:
   - **slow blink** (toggles every 500 ms) = still collecting evidence
   - **solid on** = SPI telemetry demonstration passed
   - **fast blink** (toggles every 100 ms) = failing

## 7. Variables and expected values

Everything lives in one global struct, `spi_test`.

| Field | Meaning | Expected in a good run |
|---|---|---|
| `result` | `SPI_TEST_RUNNING` (0), `SPI_TEST_SPI_TELEMETRY_DEMO_PASSED` (1), `SPI_TEST_FAILING` (2). Not latched: it reflects the current state. | 0 for the first ~5 s, then **1** and stays 1 |
| `sck_hz` | SPI clock computed from the live clock tree | **125000** |
| `raw[5]` | Last response bytes exactly as received | `raw[0]` = 0x00, `raw[1..4]` non-zero and changing every poll |
| `status` | `raw[0]` | **0** |
| `uptime_s` | `raw[1..4]` decoded as a little-endian float | About the seconds since the PIB powered up or reset, rising about 0.5 per poll |
| `polls` | Poll attempts | Goes up by 2 each second |
| `valid_samples` | Polls that passed every check | Equal or nearly equal to `polls` |
| `hal_errors`, `last_hal_status`, `last_spi_error_code` | HAL transfer failures (any transaction) and the last failure details | **0** |
| `invalid_responses` | Responses rejected for any reason. Broken down in the next five rows. | **0** |
| `zero_responses` | All 5 bytes were 0x00 (MISO dead, CS not reaching the PIB, or PIB not running) | 0 |
| `ff_responses` | All 5 bytes were 0xFF | 0 |
| `bad_uptime` | Uptime NaN/inf, ≤ 0, or > 1e6 s | 0 |
| `unexpected_status` | Status ≠ 0x00 | 0 |
| `uptime_stalls` | Uptime did not increase since the last accepted sample | 0 |
| `uptime_resets` | Uptime went backwards (PIB reset). Starts a new evidence window; not counted as invalid. | 0, unless you reset the PIB on purpose |
| `consecutive_valid` | Valid samples in the current evidence window | Keeps growing |
| `window_start_uptime_s` | PIB uptime at the start of the window | — |
| `uptime_progress_s` | How much PIB uptime advanced during the window | About equal to `nucleo_elapsed_s` |
| `nucleo_elapsed_s` | Nucleo time elapsed during the window | — |
| `progression_ok` | 1 when the progression rule (below) holds | **1** |
| `passed_ever`, `first_pass_poll` | Whether a pass has ever been reached, and at which poll | 1, about 11 |
| `last_valid_ms` | Nucleo tick of the last valid sample | Keeps increasing |

**What "valid" means.** `HAL_OK` alone proves nothing, and neither do repeated zero bytes. A sample counts only if all of the following hold:

- both transfers returned `HAL_OK`
- the reply is not all 0x00 and not all 0xFF
- the uptime is a finite number between 0 and 1e6 s
- the status is exactly 0x00
- the uptime is strictly greater than the previous accepted uptime

**Progression rule (pass condition).** The result becomes 1 when all three hold:

- there are **≥ 10 consecutive valid samples**
- the samples span **≥ 5 s** of Nucleo time
- `|uptime_progress_s − nucleo_elapsed_s| ≤ 10 % × nucleo_elapsed_s + 0.3 s`. The 0.3 s allows for the PIB's 100 ms snapshot refresh and poll jitter.

**Failing.** The result becomes 2 if no valid sample arrives for 10 s. It also becomes 2 if a full window (10 samples over 5 s or more) has built up but its progression doesn't match.

## 8. Running the physical test, with pass/fail criteria

1. Do the wiring and orientation checks (section 4) with both boards unpowered.
2. Verify the PIB power source (section 5). Disconnect all actuator loads.
3. Power the PIB and flash or run its normal firmware (6.5). Confirm DEBUG_LED is blinking.
4. Plug in the Nucleo and start debugging it (6.6). Add `spi_test` to Live Expressions.
5. Let it run for **at least 60 s**.
6. **Negative control 1 (MISO):** unplug the MISO wire at either end.
   - Within about 10 s, `zero_responses` should rise, `result` should go to **2**, and LD2 should blink fast.
   - Reconnect the wire. Within about 5–6 s, `result` should return to **1**.
7. **Negative control 2 (PIB reset):** press the PIB's reset button.
   - `uptime_resets` should go up by 1, and `uptime_s` should restart near 0.
   - `result` should return to **1** within about 5–6 s.

   This shows the numbers really come from the PIB.
8. Fill in `TEST_RECORD.md`.

**Pass** (record as *"SPI telemetry demonstration passed"*) when all of the following hold:

- `result` = 1, and was still 1 at the end of a ≥ 60 s run with all wires connected
- `sck_hz` = 125000
- `status` = 0x00
- `uptime_s` is plausible: it roughly matches the time since the PIB powered up or reset
- `hal_errors` = 0
- `invalid_responses` = 0, apart from those you caused on purpose in step 6
- both negative controls behaved as described

**Fail:** anything else. Record the counter values and see section 9.

Even a pass does **not** complete PIB Test 2, because I²C has not been tested.

## 9. Troubleshooting

| Symptom | Likely causes |
|---|---|
| `polls` not increasing | Nucleo is paused in the debugger (press Resume), or stuck in `Error_Handler` (pause and look at the call stack) |
| `zero_responses` rising | MISO wire open or on the wrong pin. CS not reaching J3.9, so the PIB is never selected and MISO stays at the pull-down. PIB unpowered, not flashed, or stuck in `Error_Handler` (DEBUG_LED not blinking). GND missing. |
| `ff_responses` rising | MISO shorted to 3.3 V, or wired to the wrong pin |
| `bad_uptime` or garbled `raw` | SCK and MOSI swapped. Wires too long or noisy: shorten them, or lower the speed (prescaler 256). Wrong GND. |
| `unexpected_status` | The PIB reports a status bit, and bit 0 means ARMED. **Stop**, keep the loads disconnected, and find out why before continuing. |
| `uptime_stalls` rising | The PIB's main loop isn't refreshing telemetry (PIB halted in a debugger or stuck), or the reply is stale |
| `uptime_resets` rising on its own | The PIB keeps rebooting. Check its power supply (section 5). |
| `hal_errors` > 0 | Check `last_hal_status` (3 = timeout) and `last_spi_error_code`. In master mode this is unusual; rebuild and re-flash. |
| `progression_ok` = 0 although samples are valid | The PIB's uptime runs at the wrong rate (clock configuration problem on the PIB) |
| Debugger says "No ST-LINK detected" or "target not found" | Wrong S/N selected (6.4), or the USB cable is power-only |
| PIB flashed by mistake | The S/N wasn't set. Set it in both configurations (6.4) and re-flash both boards. |

## 10. Software checks (no hardware involved)

Run these from this folder:

```sh
cd host_test && make test
```

`host_test` builds `Core/Src/spi_telemetry_test.c` together with the PIB's real `App/Src/telemetry.c` for the Mac, with AddressSanitizer and UBSan enabled. A small simulated PIB copies the `spi_slave.c` behaviour: the frame is handled on CS rise and the reply is loaded for the next transaction. The test runs 20 s of simulated time in each of these scenarios:

- normal PIB
- MISO open
- MISO stuck high
- HAL timeout
- PIB telemetry frozen
- status ≠ 0
- uptime running at 2× speed
- PIB reset partway through

In every scenario it checks the following:

- CS is high between transfers
- the PIB received no commands
- the derived SCK is 125 kHz
- polling runs every 500 ms

Then it checks that the run passes only in the normal and reset scenarios, and that each fault increments the right counter.

These checks only show that the logic matches the PIB source. **They are not evidence that the hardware works.** Only section 8 provides that.
